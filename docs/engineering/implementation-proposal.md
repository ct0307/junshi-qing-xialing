# 演义沙盘：工程落地建议

## 目标与状态

用户预计距课程交付还有一个多月。目标是在 Android 手机上离线游玩的三国沙盘塔防，最终覆盖 25 名有不同机制和可辨外观的角色、战前最多选择 10 人、每名武将每局最多招募一次、远多于 10 个阵位、不同地图和多 Boss。

当前有策划、美术生成脚本、v3 验收基准与 v4 的七位人物示范素材；没有可运行游戏工程。本文件为工程建议，技术选型和具体关卡数量不冒充用户已经最终确认。

## 技术建议

推荐 Unity LTS、C#、2D 正交相机、SpriteRenderer、uGUI 与 TextMeshPro，输出 Android APK。立项时锁定具体编辑器、包与 Android 构建组件版本。此轮只写方案，不安装工具或依赖。

此前 Kotlin 原生二维绘制的建议适合较小规模的演示；现在的重点是 25 人、多地图、Boss 阶段与动态反馈，Unity 的场景、预制体、动画和关卡编辑工具更有利于持续制作。原生 Android 仍是技术可行的备选，若课程评分要求变化再评估，不同时开发两套客户端。

首版采用本地单机与本地存档。先完成用户已讨论的战斗与关卡体验；联机、账号、付费等不进入当前排期。

## 规则与内容边界

- 从角色池中排除本关全部中场和最终 Boss，再选择最多 10 人。
- 每名守将每局最多招募一次；34 阵位示例表示位置选择多，不表示可以招募34人。
- 采用开局军饷加战斗时间收入作为初始实现建议；暂停和切后台时收入同步停止，倍速统一作用于战斗时间。
- 局内三级升级、战斗结束重置为初始建议，数值由配置管理。
- 普通兵按固定路线前进，到城门扣城防；初版守将固定驻守，不引入尚未确认的守将阵亡、售卖或换位规则。
- 胜利需要全部波次生成完毕、所有需击退敌军清除且城防大于零；城防归零即失败。
- 关卡先按5张不同布局排期，属于建议，不代表已确认数量。虎牢关作为工程样板关，不预设为玩家教程第一关。
- 首轮试玩可按每局约5～8分钟尝试，随后根据真实通关、失败和重玩体验调整，不能用单纯堆血量延长停留。

## 玩家流程

世界观以“在演义沙盘中推演战役”统一不同阵营和时期人物的搭配。各关用简短战役引子、Boss身份与招式、地图地貌和结算文字交代背景，把原著元素落实为可见的关卡差异；不宣称逐场复原历史战役。

主菜单 → 关卡与 Boss 情报 → 选将 → 布阵与自动战斗 → 胜败结算 → 下一关或重试。

招募交互采用“点人物卡—看可用阵位及射程—点阵位确认”。点击已部署人物显示升级费用和收益。余额不足、未选择人物、阵位已占用、角色已招募、角色满级均有清楚反馈；不发生无效扣款。只读查看情报不推进战斗。

## 工程拆分

| 模块 | 职责 | 关键约束 |
|---|---|---|
| BattleSession | 开局、暂停、战斗、胜败与重开 | 明确状态转换；结算仅触发一次 |
| BattleClock | 统一战斗时间与倍速 | 敌军、收入、冷却、状态、波次共用同一时间 |
| RecruitmentSystem | 选将检查、扣军饷、部署与升级 | 校验成功后作为一次完整操作提交，防止重复点击重复扣款 |
| EnemySystem | 出兵、路线进度与抵城 | 固定路径插值；不依赖复杂寻路与刚体碰撞 |
| CombatSystem | 选敌、攻击、伤害与状态 | 规则与动画分离；以命中事件触发相应反馈 |
| BossController | 出场、预告、发动、恢复及阶段切换 | 阶段清楚；控制抗性和冷却可配置 |
| BattlePresenter | 人物、血条、射程、音效和特效 | 展示状态，不决定军饷、伤害或胜负 |
| SaveService | 通关记录、设置与选将方案 | 本地保存；失败数据可恢复到默认值 |

建议工程分为 Domain（纯 C# 战斗规则）、Content（配置与素材）、Presentation（场景和显示）以及 Tests（规则与场景测试）。只对实际模块建立接口，不提前引入大型框架。

## 角色、技能与 Boss 的实现

人物身份、守将配置、Boss 配置分开。CharacterDefinition 保存唯一身份和外观引用，HeroDefinition 保存招募、升级和攻击配置，BossDefinition 保存阶段和技能配置。吕布在虎牢关作为 Boss，其他关卡作为可选守将时可复用形象，战斗行为使用各自配置。

25 人采用可复用机制加专属状态：选择目标、单体、直线穿透、扇形、范围持续伤害、减速、眩晕、增益和补给分别实现。关羽连续锁定积累刀势；赵云使用直线穿透；周瑜留下燃烧区域；张飞周期怒喝；诸葛亮提供减速覆盖；黄忠优先补漏。庞统连环与协同攻击具有伤害来源标记，防止相互递归触发。

配置使用 ScriptableObject 保存角色基础值、三级成长、技能参数、路线节点、阵位、波次和 Boss 表。运行时创建独立战斗状态，不修改共享配置，避免重开后残留升级和生命状态。用编辑器校验角色ID唯一、路线有效、阵位不落在禁区、全部Boss排除于可选池。

Boss 采用“预告—发动—恢复”的状态流程。先实现可辨认的单一机制，再加入生命阶段；对眩晕、减速和技能干扰设置明确抗性或间隔，避免永久控制。多Boss按全关威胁预算分配血量和出场间隔。

## 美术与 UI 接入

- v3 作为视觉验收基准，v4 精修素材作为接入资源；价格、伤害和血量演示数字不能当成已验证平衡值。
- 当前整张战斗图仅作对照。游戏应分为静态地表道路、建筑、可交互阵位、人物、投射物、特效和 UI 层；重新导出不含空阵位底座的背景，阵位状态由程序绘制。
- 示例图中四个已部署点也属于34个可用位置；实际开局由规则初始化阵位，不能将示意图里的四名武将烘焙成默认赠送角色。
- 当前人物全身图含台座，接入时以清单锚点对齐；避免同时叠加两套台座或把透明留白作为点击边界。
- 人物先做待机起伏、攻击动作、受击闪白和击退消散，配合已导出的反馈序列、音效与轻触反馈。位移、缩放、透明度等由程序实现。
- 以1920×1080为参考，UI采用锚点布局并适配安全区；地图与UI分别缩放，保证路线完整可见。
- 文本、数值、按钮和武将卡必须为运行时组件，使用可分发的中文字体。不得将整张设计稿作为不可交互背景替代实际UI。
- 招募、攻击命中和Boss预告的视觉时刻必须对应实际事件。暂停后战斗特效停止，暂停菜单仍可操作。

## 四轮开发与验收

| 优先级 | 时间建议 | 可验收成果 | 通过标准 |
|---|---|---|---|
| P1 | 第1周 | 真机可玩的虎牢关样板 | 现有六位守将、34阵位、张辽和吕布；选将、招募、升级、波次、胜败、暂停、重试闭环；Android APK可安装 |
| P1 | 第2周 | 完整角色系统与内容工具 | 扩展至25人配置和技能；同关Boss过滤；路线、阵位、波次可编辑；主要数值可批量调整 |
| P1 | 第3周 | 内容与美术整合版本 | 完成25人可辨素材；按最终确认数量制作不同地图和Boss；主菜单、情报、选将、结算及本地存档连通 |
| P1/P2 | 第4周 | 课程交付候选版本 | 真机屏幕与触控适配、最大波次压测、重开及后台恢复验证、难度调整；整理APK、工程、演示和说明 |

样板关使用六位守将只是开发顺序，最终目标仍为25人，每局最多选择10人。各周以验收成果推进，排期估计需在第一周真机版本后依据实际效率调整；最后阶段保留修复时间。

## 玩法平衡与验证

- 至少用输出、控制、辅助的不同组合试玩，验证存在多种可行阵容；基础军饷不能依赖某位经济角色，基础容错不能依赖华佗。
- 按敌军生命、速度、路线长度和有效射程衡量单位收益；改变路线、兵种组合与覆盖关系，避免25个角色只有面板数字不同。
- 记录本地试玩的通关时间、城防剩余、军饷曲线与角色使用情况，辅助调参；不为课程演示搭建外部数据服务。
- 测试重复点选、余额不足、已招募、满级、空阵容、同关Boss、最后一个敌人抵城、Boss死亡与最终结算的边界。
- 测试暂停、倍速、切后台与恢复后，战斗时间、军饷、冷却和状态时长一致，重开不残留上一局状态。
- 使用对象池管理敌兵、投射物和特效，按实际最大波次测试；在选定Android真机以稳定60帧为性能目标，通过Profiler找实际瓶颈。
- 视觉验收对照v3，确认角色、道路、文字和按钮层级，以及34阵位的准确点击；在宽屏、标准比例和异形屏安全区检查显示。

## 最终交付

可离线游玩的Android APK、可重新打开和构建的Unity工程、配置与素材源文件、项目启动与构建说明、玩法说明及课程演示材料。实际交付前需完成真机完整通关与安装验证，不能用静态稿或编辑器画面代替。
