# 演义沙盘：背景音乐与音效方案

版本：v1.0｜日期：2026-11-06｜状态：设计基准归档；本轮实际交付与验证见[audio-implementation-plan.md](audio-implementation-plan.md)和[音频交付说明](../audio/README.md)。下文“当前”“本轮仅设计”保留设计时点语境。

适用工程：Unity 6.3 LTS 6000.3.28f1、C#、uGUI，Android横屏离线塔防。

素材路线：用户已选择“授权素材＋原创编辑”。本方案按无新增付费预算作为排期工作假设；实际曲目、作者及许可须选材后逐项确认。

## 1. 声音目标与首发边界

声音定位为“案上推演，战阵有力”：菜单有青绿山水的留白，战斗有棋兵交锋的清楚轮廓，危险到来时立即听得出来。配乐服务于连续5～8分钟的布阵观察，节奏推动感优先于持续的高响度。

现状核对：GameAudio只有按钮、招募、升级、命中、Boss预警、胜利和失败7类程序合成短音；使用两个2D音源，提供音效总开关。尚未接入BGM、分组混音、分音量设置或角色音色。现有音效也没有完成专项听感验收。

| 路线 | 制作量与收益 | 本项目取舍 |
|---|---|---|
| 两首完整音乐＋少量提示音 | 接入快，关卡与Boss区分有限 | 工期压缩时的保底版本 |
| 共享主题、五关预混版本、公共Boss段 | 关卡有区别，常规播放即可接入 | 首发推荐 |
| 五关独立作曲、同步分轨和角色配音 | 内容与联调量明显增加 | 后续扩展 |

首发交付预算：9个音乐文件＋34个音效文件，共43个运行时音频文件。音乐含7个循环与2个结算短句；音效含31个共享文件与3个武将标识。制作清单共28个Cue条目，变体按文件数展开。环境声、额外Boss音色和角色语音不计入首发数量。

若找不到允许编辑和工程交付的分轨素材，先完成菜单、公共战斗、Boss和两段结算共5个音乐文件。保底将music.battle.huangjin对应文件mus_battle_huangjin_v01作为公共战斗曲，五关music.battle.*均绑定它；另外4个关卡混音任务在保底范围内降为P2。此时配合34个音效为39个文件。CSV的“保底处理”列明确哪些任务复用、哪些延期；不采用分离人声等方式假定获得授权。

## 2. 配乐制作简报

### 2.1 编制与主题

主导乐器选择琵琶或筝的短拨弦，配箫、笛的中低音区，笙或薄弦乐承托，堂鼓、木质击节和少量铜响推进。常态突出约4～6层，保留短旋律和较长呼吸；Boss段增加节奏密度与中频厚度。

统一使用一个简短的五声性动机贯穿菜单、战斗与胜利。它是新编主题的工作方向；选用授权配乐时，优先寻找同作者、同风格且允许编辑的成套素材，再以统一过门和配器建立联系。所有新增乐器采样也须记录许可。

避免持续占据高频的笛音、全程密集大锣、过长混响和依赖超低频的鼓底。角色和战场是微缩演义沙盘，音效可加入木质落子感；表现不以历史乐器复原为验收条件。

### 2.2 首发音乐清单

以下为创作与选材目标，不是Unity或Android强制标准。时长可随合法素材的小节结构调整，最终以实际导出的整数采样点为准。

| Cue | 工作名与用途 | 节奏与长度 | 文件数 |
|---|---|---|---:|
| music.menu | 案上山河：主菜单、选关、情报、选将和备战 | 80 BPM，4/4，24小节，约72秒循环 | 1 |
| music.battle.* | 列阵：五关常规交战，共用结构与动机 | 96 BPM，4/4，48小节，约120秒循环 | 5 |

## 4. 事件映射与同步规则

现有BattleView已经统一分发Domain事件，继续在同一次DrainEvents循环中把事件交给视觉和音频。音频不另行消费事件，不决定军饷、伤害或胜负。

| 当前事件／状态 | 首发声音处理 | 接入约束 |
|---|---|---|
| UI按钮、TryRecruit/TryUpgrade返回值 | 一般按钮播click；实际操作失败播reject；成功播对应确认 | 需调整UiFactory与操作入口，避免通用点击和拒绝声机械叠播 |
| recruit / upgrade | 入阵、进阶；3名武将使用入阵标识替换 | 由HeroId查角色；成功事件才发确认声 |
| attack | 按HeroId及Skill选择六组出手音 | 每次施放合并；同帧多目标只保留代表声 |
| hit | 播共享命中声，独立限频 | 使用已有TargetEnemyId；不假设有护甲材质字段 |
| fire / stun / slow | 突出点燃、控制起始，补充同类出手的质感 | 与attack按同一施放窗口合并；持续伤害与多目标控制不叠响 |
| kill | 敌兵退散轻音；Boss离场影响音乐状态 | 普通击退限频；终局同帧让位结算 |
| wave / IsWaveActive | 新波短提示；波间降低音乐强度 | wave每波一次；波间读取状态变化，不新增规则 |
| leak | 城防受损信号，连续漏兵合并 | 首次及时播放；终局同帧由失败短句接管 |
| boss_warning / boss_phase | 危险与阶段分别使用独立Cue | 预警及时触发，不等待音乐小节；去重窗口和阶段范围见下文 |
| victory / defeat | 停普通声、淡出BGM、完整播放一次结算短句 | 以当前会话终局去重；不因重复回调重播 |
| notice | 首发保留文字与视觉反馈 | 不解析中文Text来决定Boss登场、治疗或补给声音 |

### 4.1 需要补齐的事件身份

当前TargetEnemyId字段已存在，但主要由hit填写；kill、leak、boss_warning和boss_phase没有可靠逐敌标识，Boss登场目前只是通用notice。

接入时为上述敌人事件填入已有TargetEnemyId；需要明确登场提示时新增boss_spawn并带敌人ID。若后续需要Boss施法、治疗或军饷补给成功声，再分别增加boss_cast、heal、supply等结构化事件。保留原文字提示，不依据文案匹配声音。

Boss音乐首发可以直接读取Session.Enemies中Definition.IsBoss的活跃ID集合：0变为非0时进入Boss段，最后一名离场且战斗未终结时回常规曲。多Boss共用一首压力段，追加Boss不重启音乐。逐敌预警使用补齐后的事件ID；数据暂缺时只做一次全局合并提示，不伪造敌人身份。

boss_warning只在同批事件或150毫秒真实时间窗口内按敌人ID去重，同一Boss稍后再次预警仍可播放。boss_phase在当前仅有第二阶段的规则中按“当前会话＋敌人ID＋第二阶段”只响一次；将来增加多个阶段时必须补阶段编号，不能把敌人ID当成永久屏蔽键。重试清空以上记录。

stun当前可能没有HeroId，因此首发采用通用控制质感。张飞等角色的入阵标识已可利用recruit的HeroId，专属控制技能音待来源身份补齐后再扩展。

### 4.2 无延迟与合并窗口

操作确认、Boss预警和漏兵首个提示收到事件后立即分配音源；不为等待音乐节拍而推迟。初始出手合并窗口80毫秒，同武将或同类多目标只响一次。合并仅影响听觉，不改变伤害、特效或规则事件。

普通战斗新声音初始上限16次／真实秒；同武将出手间隔至少100毫秒，命中全局间隔100～160毫秒，普通击退250毫秒，连续漏兵400毫秒合并。超额普通声音直接丢弃，不排队补播。具体数值须按满10人、最大敌群的试听修订。

## 5. 页面与战况的音乐状态

状态裁决顺序：系统挂起静音 ＞ 手动暂停 ＞ 终局 ＞ 活跃Boss ＞ 普通交战 ＞ 波间 ＞ 备战／菜单。这里的优先级只用于声音；游戏规则状态继续由BattleSession与GameFlow决定。

| 情境 | 配乐与音效行为 |
|---|---|
| 主菜单、选关、情报、选将 | 共享menu；同一首继续播放，切页不从头开始 |
| 备战布阵 | 延续menu并降低约3dB；入阵、升级和界面反馈正常 |
| Preparation变为Running | 约1秒淡出menu并淡入本关battle；由实际开战触发 |
| 波间 | 常规曲继续，约0.3秒内降低3dB；下波恢复，避免频繁换曲 |
| 第一名Boss在场 | 约0.8～1.2秒切boss；技能危险提示立即响起 |
| 多Boss与阶段变化 | 不叠多首音乐、不逐次重启；阶段提示独立，预警同帧同类合并 |
| 最后一名Boss离场 | 未终局时约1秒回本关battle；终局由结算接管 |
| 手动暂停 | BGM短淡出后Pause保留位置；普通短音停止，UI仍可操作 |
| 胜败结算 | BGM约0.2秒淡出；结果短句播放一次，结束后接低音量menu |
| 重试／重新选将／退出战斗 | 取消旧会话排程、清空普通声与Boss集合，按目标页面重新裁决 |
| 系统后台／锁屏／失焦 | 全部声音立即挂起；包含菜单、备战和结算；不写入用户音量偏好 |
| 回到前台 | 运行中战斗仍保持系统暂停，用户继续后恢复BGM；非战斗页可短淡入恢复页面音乐，过期结算短句不补播 |

Boss预警时，Music在约60毫秒内临时降低6dB，保持约0.8秒，再用约0.35秒恢复；普通战斗声可同时降低约3dB。此操作称为压低背景音，用于突出危险信号。重叠预警延长保持时间，不累加衰减幅度。

2倍速只加快游戏模拟，BGM保持原速度和pitch=1。短音也不因倍速整体变调；按真实时间限流，避免声音密度翻倍后堆叠。

## 6. Unity最小接入设计

### 6.1 服务与资源组织

保留GameAudio作为表现层音频入口，内部拆出简单的音乐切换和短音池即可。音频配置独立于Domain的Definitions.cs与关卡数值，不增加第三方中间件或框架。

建议新资源位于UnityGame/Assets/Resources/Audio/：Music、Sfx、Config三个子目录；混音器放Assets/Audio/Mixer。独立目录便于保持现有Game内容清单的73个资源校验边界。配置记录CueId、资源路径、变体、增益、冷却、逻辑优先级、并发上限与循环属性。

短音在进入可交互页面前预载；音乐按当前与下一首按需加载。音频表存资源路径，避免直接引用所有长曲导致常驻。切换前确认下一曲就绪，失败时保留当前曲或安静退场，不阻塞战斗；切换结束清除旧引用并释放可释放资源。

音乐缺失时不反复重试刷日志；关键提示素材缺失时可回退现有合成短音，开发日志每Cue只提示一次。制作完成并验收后再决定是否移除回退。

### 6.2 混音与音源预算

原生AudioMixer结构：Master下分Music和SFX；SFX下分UI、Battle、Critical。用户看到“音乐”“音效”两个音量项与独立静音，主菜单和暂停页均可设置；内部子组由制作人员调平。

| 项目 | 初始预算／规则 |
|---|---|
| 音乐 | A/B两个2D AudioSource，交叉淡化时最多2路 |
| UI | 1个音源，同一时刻1个短音 |
| 普通战斗 | 固定6个音源，池满丢弃或抢占最低重要度的旧声 |
| 关键提示 | 固定2个音源，其中结算可抢占其他提示 |
| 总计 | 11个音源；每源同时一个片段，避免无界PlayOneShot叠声 |
| 逻辑重要度 | 结算100、Boss预警90、漏兵75、操作确认65、普通出手／命中30 |
| 初始混音 | Master预留约3dB余量；用户音乐默认50%、音效80%，最终依手机配平 |

逻辑重要度数值越大越优先；它与Unity AudioSource.priority的数值方向相反，转换时必须显式映射。普通池不能抢占关键提示池；预警和结果同帧时优先保留结果。

同一Cue选择变体时不连续重复同一文件。轻微音高变化在源级控制，关键提示保持固定音高。首发全部使用2D声，重要警报居中；声像变化仅作为P2点缀，不能成为定位危险的唯一依据。

### 6.3 时钟、暂停和设置迁移

音乐循环与排程使用DSP时钟，淡化使用非缩放时间。暂停时记住当前音乐位置并取消未来播放请求；恢复时重建时间基准，不补播历史伤害和过期预警。跨页、重试和异步加载使用会话／请求版本号，拒绝旧回调恢复旧曲。

系统音频挂起独立于PauseForSystem的Running判断；即使在菜单或结算也能停音。OnApplicationPause与OnApplicationFocus重复通知要幂等，只有所有挂起原因解除后才允许恢复。用户静音、手动暂停和系统挂起分别保存，任何恢复动作都不能覆盖另外两种状态。

新设置使用音乐／音效开关、各自0～1音量和迁移版本号。第一次读取新设置时：若旧yanyi.audio.enabled为0，则两类均关闭；旧值为1或无旧键则按默认开启。只迁移一次，后续优先新设置；保存值须限制在有效区间，0音量对应静音。旧Enabled接口过渡期兼容两类总开关，页面入口同步改成独立控制。

## 7. 音频制作、导入与授权

### 7.1 制作交付规格

所有数值都是首轮制作与测试目标，须经真实素材、编码结果和设备听测调整。

| 项目 | 初始制作目标 |
|---|---|
| 无损母版 | WAV PCM，48kHz／24bit；音乐立体声，短音效原则上单声道 |
| 音乐响度 | BGM约−20至−18 LUFS-I；结果短句约−18至−16 LUFS-I |
| 短音平衡 | 按类别和听感配平，不给极短提示强行套统一LUFS指标 |
| 峰值 | 成品母版真峰值≤−1dBTP；编码后及多音叠加另行检查 |
| 循环 | 提供BPM、拍号、小节数和起止采样点；去掉多余首尾空白，回绕混响尾部 |
| 接缝验收 | 在Unity目标平台导入设置下连续听至少3次循环；不得有爆点、断拍或异常吸气感 |
| 手机兼容 | 单声道折叠后旋律与警报仍完整；主要信息不依赖极低频或极端左右分离 |

原始素材、剪辑工程与无损母版留在制作目录；运行时导入文件按CueId命名，变体以_v01、_v02区分。音乐可使用可读短名，如mus_battle_hulao_v01；最终绑定依据CueId而非中文展示名。

循环按完整小节制作，实际循环边界落到整数采样点。整曲切换采用等功率淡化并试听叠加峰值；首发不承诺不同BPM曲目的节拍同步。对授权分轨的编辑保持版本、BPM和循环边界一致，避免不同混音长度不一致。

### 7.2 Android导入与运行预算

长BGM先用Vorbis、Streaming，立体声；短提示和攻击先用单声道PCM、DecompressOnLoad。长音只预载当前与下一首；短音预载完成后才允许首个反馈，避免首次操作卡顿。音质档位通过目标设备试听确定，不把编辑器导入界面的质量值当作固定码率保证。

初始预算：运行音频内存峰值≤24MiB、同时播放≤11声、音频CPU占用目标≤3%、APK音频增量目标≤18MiB。它们是定位问题的工程预算，不是性能保证；以选定演示手机的Unity Profiler、实际APK体积及至少一局连续运行记录为准。

导入后复核Preload Audio Data、Load In Background和加载状态的组合。Streaming音乐仍需等到可播放状态才切换；短PCM音频解压后内存按实际采样率、声道与时长计算。采样率允许按目标设备与音质需求在导入时下采样，保留48kHz母版。

### 7.3 授权素材＋原创编辑流程

优先选择CC0或明确允许修改、游戏分发及Unity工程内音频文件交付的授权素材。CC BY素材保留完整署名与许可说明。Freesound、OpenGameArt等仅作为检索入口，每条资源独立核对，不能把网站名当成授权证明。

选材时同时确认是否允许裁切、循环、叠层、音高变化和随工程交付原文件；仅允许成品游戏使用的素材可能不能随Unity源工程分发。原创剪辑不会消除原始素材的许可要求。尚未选定素材，因此本方案不声称任何具体曲目已经获得许可。

每个最终文件台账至少记录：CueId、文件名、作者、来源URL、许可证名称与版本、许可原文或凭据、下载日期、允许的分发范围、编辑记录、署名文字与SHA-256。随交付提供授权说明；第三方素材母版仅在许可允许的范围内一并交付。
